# SkyGeni Sales Intelligence System
### Win Rate Driver Analysis + Forward-Looking Risk Scoring

> **Dataset**: 5,000 B2B SaaS deals across 5 quarters (2023-Q1 to 2024-Q1)  
> **Core Problem**: CRO's win rate dropped — diagnose why, score current risk, and design an alert system.

---

## The Problem in One Paragraph

A B2B SaaS company's CRO reports that win rate has dropped while pipeline volume remains healthy. The real problem is not just the decline itself — it is that the organisation has no systematic way to decompose *why* it dropped. Without decomposition, any intervention is a guess. This system provides that decomposition, separating **conversion deterioration** (sales execution problem) from **deal mix shift** (targeting strategy problem), and then applying the findings forward to score risk in the current open pipeline.

---

## Solution Approach

**Core engine: Win Rate Driver Analysis**  
The solution focuses on building a Win Rate Driver Analysis engine to identify the underlying factors behind the decline in win rates. Since the CRO’s main concern is understanding why performance has dropped despite a healthy pipeline, the primary objective is to uncover patterns across segments such as industry, region, product type, deal size, and sales behavior. This enables clear root-cause diagnosis instead of surface-level metrics.

**Hybrid extension: Forward-Looking Risk Scoring**  
After diagnosing *why* win rate dropped historically, we apply the same risk factors to currently open deals. This converts a backward-looking diagnosis into a forward-looking action list for reps and managers.

**Monitoring hook: Preview**  
The alert engine defines the 5 metrics that, if monitored weekly, would have caught this win rate decline 6-8 weeks earlier. This grounds the monitoring design in practical, executable logic rather than a purely conceptual system description.

## Key Findings (Expected Insights After Running the Analysis)

> Run the notebooks to generate the exact results. The points below outline the **types of insights** the analysis is designed to uncover.

1. **Win Rate Trends & Variability**
   The analysis will likely reveal how win rates change across quarters, highlighting periods of decline, stability, or recovery and helping identify when performance shifts begin.

2. **Impact of Deal Mix vs True Conversion Changes**
   The system is designed to test whether observed win-rate changes come from shifts in pipeline composition (industry, product, deal size, etc.) rather than actual sales execution decline — guiding whether strategy or execution needs adjustment.

3. **Sales Rep Performance Distribution**
   The analysis should identify performance variance across reps, potentially revealing coaching opportunities, uneven execution patterns, or reliance on a small set of high performers.

4. **Sales Cycle & Stage-Level Risk Signals**
   Expected insights include differences in deal progression between won and lost deals, identifying stages where deals tend to stall and early signals that indicate higher loss risk.

5. **Lead Source & Channel Quality Patterns**
   The notebooks aim to highlight which acquisition channels contribute higher- or lower-quality deals, helping diagnose whether pipeline health issues stem from specific sources rather than overall market decline.

## How to Run

### Prerequisites
- Python 3.10+
- [uv](https://github.com/astral-sh/uv) installed
- Groq API key (free at [console.groq.com](https://console.groq.com)) — optional but enables LLM narrative

### Setup (Git Bash / Terminal)

```bash
# Clone the repository
git clone https://github.com/KRT2002/skygeni-sales-intelligence.git
cd skygeni-sales-intelligence

# Install uv (if not already installed)
curl -LsSf https://astral.sh/uv/install.sh | sh

# Create virtual environment and install dependencies
uv sync
source .venv/Scripts/activate    # Git Bash on Windows
# or: source .venv/bin/activate  # macOS / Linux

# Set up environment variables
cp .env.example .env
# Edit .env and add your GROQ_API_KEY
# If no key is set, analysis still runs — LLM narrative falls back to templated output

# Register kernel for Jupyter
python -m ipykernel install --user --name skygeni --display-name "SkyGeni"
```

### Run the Analysis


## Custom Metrics (Part 2)

Five novel metrics invented for this analysis, each solving a specific diagnostic gap:

| Metric | What It Measures | Why Standard Metrics Miss This |
|--------|-----------------|-------------------------------|
| **Win Rate Momentum Score** | Rate of change of win rate (z-scored) | Current win rate hides whether you're improving or declining |
| **Deal Mix Shift Index** | How much pipeline composition changed vs. baseline | Win rate can drop even if conversion improves — if you chase harder deals |
| **Rep Divergence Index** | IQR spread of rep win rates over time | Average rep performance masks whether the best are stable and bottom declining |
| **Stage Velocity Score** | Days per stage vs. historical baseline | Total cycle time hides *which stage* is causing the slowdown |
| **Lead Source Quality Decay** | Per-source win rate premium trend | Aggregate lead source win rate hides whether your best channels are degrading |

## Key Engineering Decisions

**Why `src/` Python modules + notebooks (not just notebooks)?**  
Notebooks are for exploration and presentation — they should be readable, not cluttered with helper functions. All reusable logic lives in `src/` modules with clear docstrings, so the notebooks stay as narrative + output. This also makes the src modules independently testable.

**Why Gradient Boosting for risk scoring?**  
With 5,000 rows and 6 features, any reasonably regularised model will perform similarly. Gradient Boosting was chosen because its feature importances are stable and interpretable, and it handles the moderate class imbalance (54% Lost / 46% Won) without explicit resampling.

**Why Kitagawa-Oaxaca-Blinder for Simpson's Paradox?**  
This decomposition method is standard in economics for separating "composition effects" from "wage effects". It is the correct mathematical tool for the question "how much of the win rate change is targeting vs. execution?" Most sales analytics tools do not implement this.

**Why statistical significance testing?**  
With 20+ segments across 4 dimensions, some will show large win rate changes by chance (multiple comparisons problem). Chi-square tests filter real signals from noise, ensuring recommendations are based on statistically robust findings.

**Why uv instead of pip?**  
Faster dependency resolution, deterministic lockfiles, and better virtual environment management. The `pyproject.toml` format is the modern Python standard.

## Part 5 – Reflection

### Weakest Assumptions

The weakest assumption is that `outcome` is recorded accurately and promptly in the CRM. If deals are marked "Lost" only after end-of-quarter cleanup, 2024-Q1 appears artificially worse than earlier quarters simply because it has less cleanup time. Before drawing strong conclusions from the 2024-Q1 drop, validate the distribution of `closed_date` relative to quarter boundaries.

The second weakest is that `sales_cycle_days` is observable at scoring time. In production this feature would need to be "days elapsed so far" not "total cycle days" — the final value isn't known until the deal closes. For the temporal split (train on 2023, score 2024-Q1), this is less of an issue since we are scoring already-closed deals, but it matters for any genuinely real-time scoring system.

### What Would Break in Production

**CRM data staleness** is the most likely failure. Reps don't update stages in real time, deals sit "open" past their actual close, and the "Closed" stage gets used inconsistently. The ingestion layer needs a schema contract with explicit validation at every sync.

**Model calibration drift** would go undetected without monitoring. If the company enters a new market or changes ICP, the 2023-trained model's distribution no longer matches incoming deals. Monthly AUC monitoring on fresh cohorts catches this before it causes bad prioritisation decisions.

**Alert fatigue** would emerge quickly in production. The alert engine as built fires on every statistical anomaly. Real deployment needs deduplication, severity escalation tracking, and user-configurable thresholds to prevent Monday-morning Slack floods that get ignored.

### What I Would Build Next (1 Month)

**Conversation intelligence integration** is the highest-leverage next step. The structured CRM data here captures *what* happened but not *why*. Gong or Chorus transcript data would let the risk scorer flag qualitative signals — "deal stuck in Demo for 40 days AND last call had 3 competitor mentions" — far more predictive than cycle length alone. This is also expected to significantly improve predictive power.

**Probability calibration** (Platt scaling or isotonic regression) on the risk model output, so that a "70% risk score" actually means the deal is lost 70% of the time. Currently scores are uncalibrated — relative ordering is meaningful but absolute values are not.

### Part I Am Least Confident About

The **risk scoring module**. The CV AUC of ~0.49 means the Gradient Boosting model has essentially zero predictive power on this synthetic dataset — the features do not contain enough signal to predict outcomes. The temporal split (train 2023, score 2024-Q1) is methodologically correct and the validation step honestly surfaces the model's weakness. But the intervention list and tier labels carry an implied confidence that the underlying model cannot yet support. In a real submission, I would present this as a framework proof-of-concept and be explicit that production deployment requires richer feature engineering before the scores are actionable.
